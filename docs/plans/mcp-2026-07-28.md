# Plan: MCP 2026-07-28, and whether to use the official SDK

**Status:** proposed 2026-10-02. Nothing built. Decision on the SDK: stay dependency-free for now, with a trigger to revisit (below).

## Where we are

- `src/mcp.ts` is the whole protocol core: about 220 lines of JSON-RPC shared by stdio and Streamable HTTP. It's dependency-free on purpose, so the local plugin runs with no `npm install` and no build step (README, "Run locally").
- It speaks `2025-11-25` back to `2024-11-05` (`SUPPORTED_PROTOCOL_VERSIONS`), with the `initialize` handshake.
- The HTTP transport is already stateless: POST only, no sessions, no server-initiated SSE stream (`src/http.ts`, the `/mcp` handler). Stdio sends `notifications/tools/list_changed` when an account's reach changes (`src/server.ts`).
- The room app speaks MCP Apps `2026-01-26` (`src/ui/room/boot.js`), a separate handshake between the app and its host.

## What 2026-07-28 changes

The [2026-07-28 specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/) is the biggest revision since authorization, and much of it isn't backward compatible:

- **Stateless core.** No `initialize`/`initialized` handshake and no `Mcp-Session-Id`. Each request carries its protocol version (the `io.modelcontextprotocol/protocolVersion` key in `_meta`), and a new `server/discover` call returns what `initialize` used to.
- **Standard headers** on Streamable HTTP: `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` for methods that name a tool or resource. Servers check that they agree with the body.
- **Cache hints are required** on results: `ttlMs` and `cacheScope`.
- **Multi round-trip requests** replace server-to-client requests: a tool that needs input mid-call answers "input required" and the client retries with the answers. Sampling, elicitation and roots are deprecated (they keep working for at least 12 months).
- **Change notifications** move to one opt-in `subscriptions/listen` stream.
- **Extensions** become formal. MCP Apps and Tasks (long-running work, polled with `tasks/get`) are official extensions.

None of this lets a server reach an agent that isn't running. "MCPortal can't push" stays true; see [rally.md](rally.md) for how scheduled agent tasks fill that gap.

## Decision: no SDK for now

The official TypeScript SDK reached a stable v2 (v2.3.0, 2026-10-02) that serves both protocol eras from one handler. It's the right choice for most servers. For MCPortal, today, it isn't:

- **It would end the no-install promise.** The SDK and its dependencies would have to be installed or bundled for every local install, the desktop bundle and the plugin.
- **Its main v2 benefit is one we already have.** Stateless serving over plain HTTP is how `/mcp` already works.
- **We use a small part of the protocol.** Tools, one resource and MCP Apps. No sampling, elicitation, subscriptions or tasks, which is where a hand-written server would most likely go wrong.
- **It still moves.** v2.3.0 itself changed how servers and transports are created per request.

**Revisit when** any of these happens:

- MCPortal needs a heavier feature: Tasks, multi round-trip input, or `subscriptions/listen`.
- A spec revision costs more than a few days to follow by hand.
- Compatibility bugs from hosts trace back to our protocol code more than once.

**Guarding against drift without the dependency:** check our messages against the official spec schemas in tests, using a dev-only dependency. Runtime stays dependency-free, and the tests prove we follow the spec.

## The migration

Serve both eras from the same core. Hosts will send `initialize` for a long time, and nothing about the 2025 path changes.

1. **Recognize the era per request.** A request carrying the `_meta` protocol version (or the `MCP-Protocol-Version` header on HTTP) is 2026-era. Otherwise, it's the 2025 path as today.
2. **`server/discover`.** It returns what `initialize` returns today: capabilities, server info, icons and instructions. Build both from one function so they can't diverge.
3. **Headers on HTTP.** Check `Mcp-Method` and `Mcp-Name` against the body on 2026-era requests, and reject mismatches with a coded error. 2025-era requests don't send them.
4. **Cache hints.**
   - `tools/list`: `cacheScope: 'private'`, `ttlMs: 0` to start. The list depends on the account's reach (`publicToolList`) and changes when someone links an account or claims a handle. A short TTL is a later optimization.
   - `resources/list` and `resources/read` of the room: private, and short-lived, since the room HTML changes with each release.
   - Tool results: private, `ttlMs: 0`.
5. **Tool-list changes on HTTP.** Stdio keeps sending `list_changed`. Over HTTP, a TTL of 0 means clients refetch. We don't implement `subscriptions/listen` until a host needs it.
6. **The room app.** No change: MCP Apps becomes an official extension and keeps its handshake. We keep declaring it in `server/discover` the way we do in `initialize`.
7. **Out of scope:** multi round-trip input, Tasks and `subscriptions/listen`. Each would arrive with a feature that needs it, and is also the moment to revisit the SDK.

## Before building

- **Find out what hosts send.** Log the protocol version from `initialize` (and, after step 1, the era) on the hosted server for a week. Record Claude, ChatGPT, Codex and Claude Code in [host-compatibility.md](../host-compatibility.md). If no host sends 2026-era requests yet, the migration can wait for the first one that does.
- **Pick the schema source** for the drift tests: the spec repository's published JSON schema, or the SDK's types as a dev dependency.

## Tests

- **Both eras:** `initialize` + `tools/list` and `server/discover` + `tools/list` return the same tools, capabilities and instructions.
- **Header mismatches:** a 2026-era request whose `Mcp-Method` or `Mcp-Name` disagrees with the body is rejected; a 2025-era request without them still works.
- **Cache hints:** every 2026-era result carries `ttlMs` and `cacheScope`.
- **Schema check:** captured messages from both eras validate against the official schemas.

## Size

Small to medium: steps 1–5 touch `src/mcp.ts`, the `/mcp` handler in `src/http.ts`, and their tests.
