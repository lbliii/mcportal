# Plan: MCP 2026-07-28

## Why

The [2026-07-28 MCP specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/) makes the protocol stateless, and much of it isn't backward compatible. MCPortal speaks only the earlier versions, so a client that speaks only the new one can't use it. Hosts will keep sending `initialize` for a long time, so the goal is to serve both eras from the same small core, still without a runtime dependency. Nothing here is built yet.

## Where MCPortal is

- `src/mcp.ts` is the whole protocol core, shared by stdio and Streamable HTTP, and dependency-free so the local plugin runs without `npm install`.
- It negotiates `2025-11-25` back to `2024-11-05` (`SUPPORTED_PROTOCOL_VERSIONS`) through the `initialize` handshake. There is no `server/discover`, no per-request version envelope, no result discriminator and no cache hints.
- `/mcp` in `src/http.ts` is POST-only and sessionless, which is useful groundwork but not conformance. It accepts JSON-RPC batches of up to 20 messages and doesn't read the new routing headers.
- The room's MCP Apps handshake (`2026-01-26`) is a separate protocol and doesn't change.
- `initialize` logs the requested and selected versions and a host category from a fixed list (`claude`, `claude_code`, `chatgpt`, `codex`, `unknown`); an unsupported `server/discover` call is logged the same way. No client names, capabilities or account ids are recorded.

## What the new version requires

Checked against the specification and schema on 2026-10-03.

| Area | Requirement |
|---|---|
| Request envelope | The protocol version and client capabilities are required in `params._meta` on every request. Client identity is recommended, not required. |
| Discovery | `server/discover` replaces `initialize` and returns `supportedVersions`, capabilities and instructions. Server identity goes in the result's `_meta`. Reusing the `initialize` result as-is is wrong. |
| Results | Every result carries `resultType`, including ordinary tool calls. |
| Cache hints | `ttlMs` and `cacheScope` are required on cacheable results: discovery, the tool, prompt, resource and template lists, and resource reads. Tool calls don't need them. |
| HTTP | The `MCP-Protocol-Version` header must match the body, and `Mcp-Name` is required where a method names a tool or resource (with sentinel decoding for encoded names). Header failures return HTTP 400 with `-32020`; unsupported versions, 400 with `-32022`; unknown methods, 404 with `-32601`. One message per POST. |
| Deprecations | Roots, sampling and logging are deprecated. Elicitation continues as the input mechanism for multi round-trip requests. |
| Extensions | MCP Apps and Tasks become official extensions. |

None of this lets a server reach an agent that isn't running. For how MCPortal brings news back without push, see [the rally engine](rally.md#handing-back).

## No SDK, for now

The official TypeScript SDK serves both eras from one handler (`createMcpHandler`, `serveStdio`) and suits most servers. MCPortal stays without it because:

- It would end the no-install local plugin.
- Its main benefit, stateless HTTP, is how `/mcp` already works.
- MCPortal uses a small part of the protocol: tools, one resource and MCP Apps. It uses no sampling, elicitation, subscriptions or Tasks, which is where a hand-written server is most likely to go wrong.

**Revisit when** MCPortal needs Tasks, multi round-trip input or `subscriptions/listen`; when a spec revision costs more than a few days to follow by hand; or when host compatibility bugs trace to our protocol code more than once.

To guard against drift without the dependency, validate captured messages against both official JSON schemas in tests, pinned to a fixed revision, using a dev-only dependency.

## The migration

Discovery, the per-request envelope, result encoding and HTTP validation land together. Adding a version string alone would claim support that isn't there.

1. **Recognize the era per request.** A request with the version in `params._meta` is 2026-era; anything else takes today's path unchanged.
2. **`server/discover`,** built from the same function as `initialize` so capabilities and instructions can't diverge, but encoded to the new schema.
3. **Results** carry `resultType` on 2026-era requests.
4. **Cache hints:** `cacheScope: 'private'` and `ttlMs: 0` everywhere to start. The tool list depends on the account (it changes when someone links an account or claims a handle), and the room HTML changes with each release. Longer TTLs are a later optimization.
5. **HTTP headers.** On 2026-era requests, check `MCP-Protocol-Version` and `Mcp-Name` against the body, reject batches, and return the specified codes. 2025-era requests behave as today.
6. **Tool-list changes.** Stdio keeps sending `notifications/tools/list_changed`. Over HTTP, a TTL of 0 means clients refetch; `subscriptions/listen` waits until a host needs it.
7. **The room app** keeps its handshake. Declare MCP Apps in `server/discover` as in `initialize`.

Out of scope: multi round-trip input, Tasks, `subscriptions/listen` and authorization changes. Each arrives with a feature that needs it, which is also the moment to revisit the SDK.

## Before building

- Read a week of the hosted server's version logs. If no host sends 2026-era requests, the migration can wait for the first one that does. These are self-reported counts of requests, not users; a direct 2026-era request bypasses both logged methods, so silence doesn't prove absence.
- Record what each host sends in [host compatibility](../reference/host-compatibility.md).

## Tests

- **Both eras:** `initialize` then `tools/list`, and `server/discover` then `tools/list`, return the same tools, capabilities and instructions.
- **Headers:** a 2026-era request whose headers disagree with its body is rejected with the right code; a 2025-era request without them still works.
- **Encoding:** every 2026-era result carries `resultType`, and every cacheable one carries `ttlMs` and `cacheScope`.
- **Schemas:** captured messages from both eras validate against the official schemas.
- **Semantics schemas can't check:** notifications get no reply, unsupported versions negotiate correctly, tool catalogs stay per-account, cache hints never leak across accounts, and 2025-era responses are byte-for-byte unchanged.
